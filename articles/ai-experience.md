## はじめに

AIエージェント（Claude Code、Devin、Cursor など）に開発作業を任せる場面が一気に増えました。
そこで顕在化してきたのが、**「人間時代に最適化された開発環境のままだとAIが本来の力を発揮できない」** という問題です。

人間中心の開発では「自由度」と「開発体験」を優先し、品質ゲートはCIに集中させ、ローカル環境はある程度の差分を許容する、というのが常識でした。
しかしAIにとっては、この設計はむしろ足かせになります。

ここ十数年、開発組織が磨き上げてきたのは **Developer Experience（DX、開発者体験）** でした。
これからは主役が変わり、**AI Experience（AIX、AIエージェントが快適に動ける体験）** と **Review Experience（RX、人間がAIの成果物をレビューしやすい体験）** をどう設計するかが、生産性を決める時代に入ったと考えています。

- **DX 時代**：人間の自由度と開発スピードを最大化する
- **AIX 時代**：AIエージェントのフィードバックループを最短化し、扱えるコンテキストを最大化する
- **RX 時代**：人間レビュアーが AI の出力を最小コストで検証・差し戻しできるようにする

本記事は、この AIX / RX を支える土台としての開発環境構築を、3つの軸で整理します。

1. **左シフト**：品質ゲートを `CI` から `pre-commit` と `hook` へ前倒しする
2. **ローカル再現性**：PaaS で動くアプリをローカルで完全再現するためのコンテナ徹底活用
3. **コンテキスト完全性**：AIにインフラを理解させるための徹底的な IaC 化

通底するテーマはひとつ、**「AIに対するフィードバックループを最短にし、AIが扱えるコンテキストを最大化する」** ことです。

## 前提：AI時代に効く指標は「ループの長さ」と「コンテキストの完全性」

人間時代の品質設計とAI時代の品質設計を比較するとこうなります。

| 観点 | 人間時代 | AI時代 |
| --- | --- | --- |
| フィードバック遅延 | 翌朝CIで気づけば十分 | **1ターン以内に返さないと手戻りが指数で増える** |
| 環境差分 | ローカルとPaaSで多少違っても人間が補完 | **AIは差分を補完できない。再現できない＝デバッグ不能** |
| インフラ知識 | 人間が暗黙知で持っている | **コードに書いていない情報はAIに存在しない** |
| コスト構造 | 人間の時間 | **トークン × 時間 × 手戻り回数** |

AIは指摘されるまで気づかず、書いていないものは知らない。
だから「**早く気づかせる仕組み**」と「**全部コードで読める状態**」を環境側で用意してやる必要があります。

## 軸1：品質ゲートを「左シフト」する ─ CI から hook と pre-commit へ

### 従来のCI中心設計が壊れる理由

人間時代の動線はこうでした。

```text
edit → commit → push → CI実行 → 失敗通知 → 修正
```

人間はCIが落ちても翌朝対応すればいい。むしろローカルで重い検証を走らせるほうが嫌われた。

ところがAIエージェントにこの動線を歩かせると地獄が始まります。

- AIはCIログを能動的に読まない（読ませると高コストかつ遅い）
- 失敗を知らないまま次の改修を積むので、後戻りが指数的に増える
- "緑のCI" を待つあいだに人間レビュアーが律速になる
- 鉄が熱いうちに（=AIのコンテキストが鮮明なうちに）叩けない

### 解：三層構造で「書かれた瞬間」に叩く

品質ゲートを以下の三層に再配置します。

| 層 | タイミング | ツール例 | AI時代の役割 |
| --- | --- | --- | --- |
| **エディタ層** | 入力中・保存時 | LSP / Prettier / format-on-save | 構文・型のリアルタイム矯正 |
| **エージェント hook 層** | ツール実行直後 | Claude Code の PostToolUse / Stop hook | AIに即フィードバック（`exit 2`で差し戻し） |
| **pre-commit 層** | コミット直前 | pre-commit / husky / lefthook | **コミットを物理的に止める最終ゲート** |
| ~~CI層~~ | push後 | GitHub Actions など | **hookで防げないものだけ**（e2e、本番依存、長時間テスト） |

ポイントは、**同じツール（lint, typecheck）を複数の層で走らせるのは無駄ではなく、早期失敗のための投資** だということ。
エディタで気づければ最良、hookで止まれば次善、pre-commitで止まれば最終防衛、CIで止まれば敗戦処理。

### pre-commit を最大限活用するレシピ

pre-commit に寄せる候補を列挙します。

- **lint / format**：`ruff`、`eslint --fix`、`prettier`（**stage済みファイル限定**で実行）
- **type check**：`tsc --noEmit`、`mypy`（差分範囲で）
- **secret scan**：`gitleaks`。AIが `.env` をうっかりコミットする事故を物理的に防ぐ
- **差分単位の unit test**：`pytest --testmon`、`vitest related` で軽量回帰
- **AI特有のゴミ検出**：未解決TODO、`console.log`残骸、生成されがちな dead import

そしてもうひとつ重要な作法：

> **pre-commit の出力 ＝ AIへの指示書、と捉えて設計する**

エラーは stderr に整形して出す。何が悪く、どう直せばいいかが diff レベルで読める形にしておく。
そうすればAIはそのまま読んで自分で直します。

### Claude Code hook 層との役割分担

- **PostToolUse hook**：編集ツール実行直後に `tsc --noEmit` などを走らせる → コミット前に気づける
- **Stop hook**：ターン終了時に pre-commit を予行演習で走らせる → 本コミット時に詰まらない
- **pre-commit 本番**：人間がコミットする時 / AIが `git commit` する時の最終ゲート

### 落とし穴

- **pre-commit が重すぎてコミットが詰まる** → 差分限定を徹底する。フルチェックはCIに残す
- **AIが `--no-verify` で回避する** → CLAUDE.md などのルールで明示的に禁止する
- **ローカル環境差で落ちる** → pre-commit フレームワークでツールバージョンを固定する

CIの平均実行時間が10分→2分になり、AIの自走サイクルも結果的に短くなります。

## 軸2：ローカル再現性に全振りする ─ コンテナを徹底活用する

最近のアプリは PaaS（Cloud Run、Vercel、Heroku、ECS Fargate、App Runner など）で動かすケースが大半です。
便利な一方で、AIエージェントにとっては厄介な性質を持ちます。

- **ローカルで再現できない問題が増える**：環境変数、サイドカー、外部リソース、ランタイム差
- **AIはログを見ても再現できないとデバッグが止まる**：人間ならクラウドコンソールを開いて勘で進めるが、AIは勘がない
- **PaaS固有の挙動はドキュメントを読まないと分からない**：AIには見えていない

### 原則：ローカルで再現できないものは、AIにとって存在しないものと同じ

であれば、ローカル＝AIの作業場を、本番にできる限り近づける必要があります。
ここで効くのが **コンテナの徹底活用** です。

### コンテナを"開発環境のソース・オブ・トゥルース"にする

最低ラインとして以下を満たします。

- **アプリ本体**：本番と同じベースイメージで動く Dockerfile を用意する
- **依存サービス**：DB、キャッシュ、キュー、オブジェクトストレージは `docker compose` で立ち上がる
- **クラウドサービスのエミュレータ**：AWS系は LocalStack / ministack、GCP系は公式エミュレータ、など
- **PaaS固有挙動の擬似再現**：Cloud Run なら `--port` と `PORT` 環境変数、Vercel なら `vercel dev`、ECS なら `awslocal` + LocalStack
- **ワンコマンド起動**：`make dev` か `docker compose up` だけで全部起動する状態にする

ここまで揃えると、AIに対して「**この環境で再現してから直して**」という指示が成立するようになります。
逆にここが揃っていないと、AIは推測でコードを書き、本番で初めて壊れる、という最悪のループに入ります。

### OSS エミュレータを最大限に活用する

ローカル再現性の鍵を握るのが、クラウドサービスを擬似再現する OSS エミュレータ群です。
最近は選択肢が一気に充実してきており、AI時代こそ積極的に取りに行きたい領域です。

- **[LocalStack](https://github.com/localstack/localstack)**：AWS 系を広範にカバーするデファクト。S3 / SQS / Lambda / DynamoDB / API Gateway などをローカルで再現できる
- **[ministack](https://github.com/ministackorg)**：軽量に AWS 互換 API をローカルで動かす OSS。LocalStack より起動が軽く、CI や AI エージェントの作業ループに組み込みやすいケースがある
- **Pub/Sub エミュレータ / Firestore エミュレータ**：GCP系は公式エミュレータが充実
- **[Azurite](https://github.com/Azure/Azurite)**：Azure Storage のローカルエミュレータ

選び方の観点としては：

- **起動の軽さ**：AIのループに毎ターン挟むなら、起動が遅いエミュレータは致命傷になる
- **互換性の範囲**：使っている API が再現されているかを事前に確認する
- **`docker compose` 一発で立ち上がるか**：Dev Container や CI に組み込みやすい

「クラウドだから再現できない」と諦めずに、**まず OSS エミュレータを探す** という習慣をチームに定着させるだけで、AIの自走領域は大きく広がります。

### Dev Container / コンテナ統合エディタの活用

Claude Code や Cursor などのAIエージェントを **Dev Container 上で動かす** のもおすすめです。

- AIが触るシェルが本番に近いLinux環境になる
- ホストOS差（macOS / Windows）に起因するAIの混乱が消える
- チーム全体で「AIに与える環境」を統一できる

「AIの作業場を環境ごとコードで固定する」発想は、AI時代に必須の習慣だと考えています。

## 軸3：徹底的な IaC で「インフラのコンテキスト」をAIに渡す

ローカル再現性を高めても、もうひとつ残る問題があります。
**「AIには本番インフラが見えていない」** ことです。

### コードに書いていないものはAIに存在しない

AIエージェントが扱えるコンテキストは、原則としてリポジトリ内のテキストとツール経由で取れる情報だけです。
本番インフラの設定が、

- AWSコンソールでポチポチ作られている
- 古いランブックの Notion ページにだけ書いてある
- 担当者の頭の中にだけある

という状態だと、AIはそれを **「存在しないもの」として推論する** しかありません。
結果、ローカルでは動くのに本番で動かない、セキュリティグループが足りない、IAMが足りない、といった事故が頻発します。

### IaC の役割は「実行」より「読める状態にする」こと

IaC（Terraform、Pulumi、CDK、SAM、Serverless Framework など）の従来の主目的は **再現性のあるデプロイ** でした。
AI時代に追加される目的はもうひとつ、**「AIに読めるインフラドキュメントとして機能させる」** ことです。

これを満たすには：

- **本番に存在するものは漏れなくコードに書く**：手作業で作ったリソースをゼロにする
- **環境変数・シークレットの参照経路までコード化する**：Secrets Manager / SSM Parameter Store の参照を IaC に書き切る
- **依存関係を読み取れる粒度で書く**：モジュール分割が荒すぎるとAIが追えない
- **ネットワーク・IAM・スケーリング設定を必ずコードに含める**：「動かない原因」が大体ここに集中する

### IaC × ローカル再現の合わせ技

軸2のコンテナ環境と軸3のIaCをつなぐと、こうなります。

```text
[本番インフラ] ←─ Terraform / CDK で定義 ─→ [リポジトリ内コード]
                                                  │
                                                  ├─ AIが読み取って理解
                                                  │
                                                  ▼
                                          [docker compose / LocalStack で再現]
                                                  │
                                                  ▼
                                          [AIがローカルで検証→修正]
```

AIから見ると、**「本番と同じ構造のものがローカルで動き、定義はリポジトリに全部ある」** 状態になり、推論の根拠が大幅に増えます。
これは人間にとっても同じく恩恵があり、新メンバーのオンボーディングコストも下がります。

## 補論：意図的に「コンテキストを渡さない」という戦略

ここまでは「AIに渡せるコンテキストを最大化する」という話でした。
ところが現場感覚としては、その逆 ── **意図的にコンテキストを遮断する** ことが必要な領域も存在します。

代表例が **E2E テスト** です。

普段からAIを使っている方なら、心当たりがあるはずです。

> **「実装が落ちたから直して」と頼んだら、AIが勝手にユニットテストや E2E テストの方を書き換えていてポカーンとした**

という経験、一度や二度ではないと思います。
これは AI から見ると、テストコードも実装コードも同じ「コンテキスト内のテキスト」であり、整合性を取りに行くときにテスト側を緩める手段が一番安い、という構造的な問題です。

### 戦略：E2E テストを別リポジトリで管理する

そこで取れる戦略のひとつが、**E2E テストを意図的に別リポジトリに切り出して、AIエージェントの作業対象から外す** という設計です。

- **アプリリポジトリ**：AIが自走して書く・直す対象
- **E2E テストリポジトリ**：AIから直接は触らせない、人間と CI だけが管理する場所

こうすることで得られる効果は明快です。

- AIが「テストの方を書き換えて整合性を取る」抜け道を物理的に塞げる
- E2E テストが **「AIに対する独立した契約書」** として機能する
- 失敗時の挙動が人間にとってレビューしやすくなる（= RX が上がる）

ユニットテストまで分離するのはやり過ぎですが、E2E のように **「仕様を表現するテスト」** は、AI のコンテキストから一段距離を置くほうが健全に運用できるケースが多い、というのが体感です。

### とはいえ E2E を書くのも AI に頼みたい ── "疎結合に召喚する"

別リポジトリに切り出す、と書くと「AI を使えなくなるのでは？」と思うかもしれません。
もちろん E2E テストの作成・修正自体は AI にやってもらいたいし、それは全く矛盾しません。

ポイントは、**普段は切り離しておき、必要なときだけ AI のコンテキストに"召喚する"** という疎結合な参照スタイルです。

- 通常の実装作業：アプリリポジトリだけを開く。E2E はコンテキスト外
- E2E を書く・直す作業：Claude Code の `/add-dir` などで E2E リポジトリを **明示的に追加** してから取り組む
- 終わったらコンテキストから外す（セッションを切る）

この「**常に見えている**」ではなく「**必要なときだけ覗かせる**」という設計にすることで、

- 普段の改修で AI がテストを"勝手に整合させる"事故を防ぎつつ
- E2E に手を入れたいときには AI の生産性をフルに使える

という両取りが可能になります。
要は **モノレポ的に何でも見える状態にしないこと自体が AIX の設計判断** だ、ということです。

### 結局、AIX は「何を渡し、何を渡さないか」の設計

ここで強調したいのは、**コンテキストの粒度を AI ごと・タスクごとに設計する** という発想です。

- AIに **渡すべき** もの：実装コード、IaC、README、設計ドキュメント、ローカル環境定義
- AIに **渡さないべき** もの：仕様の最終契約に近い E2E テスト、本番シークレット、人間レビュアーが守るべき基準

「AI Experience を最大化する」とは、ただコンテキストを増やすことではなく、**何を渡し、何を渡さないかを意図して設計すること** に他なりません。

## 全部つなげると：AI最大活用環境の全体像

ここまでの3軸を1枚に重ねるとこうなります。

| 領域 | 投資先 | AIへの効果 |
| --- | --- | --- |
| 品質ゲート | hook + pre-commit に左シフト | フィードバックループの最短化 |
| 実行環境 | コンテナで本番をローカル再現 | デバッグ・検証のループが回る |
| インフラ定義 | 徹底的な IaC 化 | コンテキストの完全性確保 |
| テスト・契約 | E2Eなどは別リポジトリで疎結合参照 | コンテキスト粒度の意図的制御 |
| CI | 薄く、最後の砦 | hookで防げないものに集中 |

通底する原則はやはりひとつ。

> **AIへのフィードバックを最短に、AIが扱えるコンテキストを最大に。**

## まとめ：AI時代の開発環境構築4原則

1. **左にシフトせよ**：CIにあるものを pre-commit に、pre-commit にあるものを hook に。失敗はAIが読める形で stderr に返す
2. **ローカルで全部動かせ**：PaaS固有挙動までコンテナで再現する。AIにとって"再現できない"は"存在しない"と同義
3. **インフラもコードに書け**：IaC は単なるデプロイ自動化ではなく、AIに渡すインフラドキュメント
4. **コンテキストは意図して絞れ**：渡すべきものは最大化、渡すべきでないものは物理的に分離。E2Eは"召喚式"で参照する

これまで「人間の自由度」のために緩く設計されてきた領域を、AI時代は **「AIの自走性」のために厳しく固める** 方向に反転させる必要があります。
同時に、何でも見せれば良いわけではなく、**「渡すコンテキストと渡さないコンテキストを意図して設計する」** ことが、AI と人間レビュアーの双方の生産性を引き上げます。

**Developer Experience の時代から、AI Experience と Review Experience の時代へ。**
環境への投資を惜しまない人ほど、AIエージェントを最大限走らせられる時代です。
