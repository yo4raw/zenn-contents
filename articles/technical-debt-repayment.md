# はじめに

私が現職に着任したときは
## **アレとかアレでいろいろヤバくて全然大丈ばない**
といった状況でした。
現状も道半ばですが、いろいろな人を巻き込みつつ今までやってきたとと、優先順位の付け方などを個人の経験をもとに記載します。

## 問題の一例

- 握りつぶされる例外
- 例外の中でリトライされる悲劇
- パプリッククラウドのリソースがエクセルで管理されそのエクセルがSVNで管理されている
- 書かれていない単体テスト
- 活用されず負債になるModel層なはずの化石層
- ORMのパフォーマンスが悪いと生SQLが書かれる悲劇（ORMの使い方が悪い）
- 本当にほしい情報が吐かれないlog
- 同じコードでも環境毎に挙動が違う地獄

## 問題しかない。つまり伸びしろしかない

とはいえ、なにかしら事情があって今の運用になっているはずです。
それらを解決するソリューションを知っていたけど採用できなかった理由などもあるかもしれません。
ですので、前任者あるいは既存の体制を作り上げた方々に誠意を持って、現状のだめな部分を指摘するのではなく【なぜその運用になったのか】をヒアリングしていきます。
そうすると、いくつかの問題に分類することが可能でした。

- そもそもソリューションを知らない
- 現状のオペレーションに不満を持っていない

となると、

## コスパが良い施策から実行

問題は山積みです。ですから、なにから始めるかはとても重要です。
そこで大きく下記の4つに分けました

| 工数削減 | 実装工数 | 対応優先度 |
|--------|--------|------------|
| 高 | 高 | BigPictureの作成 |
| 高 | 低 | 最優先に着手 |
| 低 | 高 | 何もしない |
| 低 | 低 | バックログに追加 |

工数削減の効果が高く、実装工数が低いものはちゃっちゃとやっちゃうに限ります。とにかくやる。ひたすらやる。
しかし問題は工数削減の効果は高いが、実装工数も高いものです。
1人で頑張ってもどうもならない部分でどうしてもいろいろな関係者を巻き込む必要が出てきます。


### コスパの良い施策の例
例えば私が入ったときは各システムがデータのやり取りをするためにS3をインタフェースとして利用していました。
そのためデータのやり取りするシステムが増えればS3のポリシーを更新する必要が出てきます。
そのポリシーの更新が下記のように行われていました。

- ExcelのAWS大腸に各ポリシーのjsonが管理されそのExcelがSVNで管理されていた
- あらかじめExcelを更新しておき、チーム全員で集まってExcelに記載されたjsonをAWSコンソールにコピペしてリリース

と

## 工数削減の効果が高く、実装工数が高い負債への向き合い方

ここはそれなりの時間をかけて負債を返済する必要があります。
ですから、「現在の問題点はこれ（こうすればもっと楽にできる）」「この問題を解決するにはこうする」「これらが実現するとこのような世界が実現できる」とある程度明確にイメージできるような青写真を書く必要があります。そしてこれは会社から予算を獲得する際にも必要になってくるでしょう。

それだけではありません。工数削減の効果が高く、実装工数が高い部分に関してはここを更に4つに分類しました。
いわゆるアイゼンハワーマトリクスですね。

| 重要度 | 緊急度 |
|--------|--------|
| 高 | 高 |
| 高 | 低 |
| 低 | 高 |
| 低 | 低 |
